# Graft

Graft is a GitHub App and service that adds intent review and policy checks to agent-written pull requests. This repo holds the service; step 1 is the base skeleton (webhook intake, job queue, installation tracking) and step 2 adds provenance (who wrote each PR, shown in a check run and the managed PR comment) and step 3 adds the intent service (a model-written intent card per PR, checked by a second model call and a rule-based risk floor); step 4 adds the evaluation set (`pnpm eval`: case format, encrypted private storage, export, labeling, harness, metrics, a synthetic CI set); step 5 adds the policy engine, report-only (`graft.yaml` read from the base branch, a `graft/policy` check that always concludes `neutral`, a `policy` section in the PR comment, `pnpm graft policy check`); step 6 adds pilots and the gate (an onboarding kit, a review-time baseline, reviewer eligibility for card votes, the Phase 0 gate report with a Wilson interval, a daily metrics rollup, incidents, `pnpm graft pilot|baseline|gate|metrics|incident`, and offboarding with `pilot purge`).

See the [MVP spec](docs/spec/mvp-spec.md), the [development plan](docs/plan/development-plan.md) and the [Phase 0 steps](docs/phase-0/README.md).

## 1. Prerequisites

- Node 24 (`.nvmrc`), pnpm 11
- Docker (OrbStack works) for Postgres

## 2. Quick start (offline)

Only `pnpm install` and the Docker image pull need the network.

```sh
pnpm install
pnpm db:up                       # Postgres 17 on localhost:55432
cp .env.example .env
openssl genrsa -out dev.pem 2048 # throwaway key so the server boots without a real App
pnpm db:migrate
pnpm dev:server                  # terminal 1
pnpm dev:worker                  # terminal 2
pnpm webhook:send installation.created --delivery smoke-1   # 202 {"status":"enqueued"}
pnpm webhook:send installation.created --delivery smoke-1   # 200 {"status":"duplicate"}
psql postgres://graft:graft@localhost:55432/graft \
  -c 'select id, account_login from installations' \
  -c 'select id, full_name, removed_at from repositories'
curl localhost:3000/readyz
```

`.env.example` already points `GITHUB_APP_PRIVATE_KEY_PATH` at `./dev.pem`. Neither process runs migrations; if the schema is behind they exit with `run pnpm db:migrate`.

Other scripts: `pnpm db:status`, `pnpm db:rollback` (reverts only the latest migration), `pnpm format`, `pnpm build` then `pnpm start:server` / `pnpm start:worker`.

## 3. Tests

```sh
pnpm test:unit          # nothing needs to be running
pnpm db:up && pnpm test:integration   # real Postgres + real pg-boss
pnpm test               # both
pnpm test:perf          # opt-in: the wall-clock (millisecond) assertions of the unit tests
```

Integration tests use `TEST_DATABASE_URL` (default `postgres://graft:graft@localhost:55432/graft_test`). `test/global-setup.ts` drops and recreates `graft_test` on every run, then migrates. If Postgres is not reachable it fails with `Postgres not reachable at <host:port>; run pnpm db:up`. A network guard (`test/setup.ts`) makes any `fetch` to a non-localhost host throw, and GitHub is only ever reached through injected fakes. Test names carry the IDs from the step spec (`U-WH-3`, `I-INST-5`, ...), so `grep -rn "I-WH-" test/` finds them. **No default test asserts wall-clock time.** Tests about the cost of glob matching, redaction and the LLM deadline assert deterministic work units (`GlobBudget` fuel, `exhausted`, `limitHits`, `pairsUsed`) in `pnpm test`; their millisecond bounds go through `expectDuration` (`test/helpers/perf.ts`) and are enforced only with `GRAFT_PERF=1` (`pnpm test:perf`), otherwise only a 30 s sanity ceiling applies. Unit tests have a 120 s timeout, integration tests 30 s.

Fixtures in `test/fixtures/webhooks/` come from `@octokit/webhooks-examples`, rewritten to one fictional world (`scripts/generate-fixtures.ts`).

## 4. Connecting a real GitHub App

1. Edit `github/app-manifest.json` (name, `url`, `hook_attributes.url`). Create a channel at <https://smee.io/new> and use its URL as the hook URL.
2. Serve `github/register-app.html` (for example `cd github && python3 -m http.server 8080`, then open <http://localhost:8080/register-app.html>), enter the org name and submit. GitHub redirects to `redirect_url` with `?code=...`.
3. Convert the code: `gh api -X POST /app-manifests/<code>/conversions`. The response has the App `id`, `pem` and `webhook_secret`.
4. Put the PEM in a file outside the repo and fill `.env`: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY_PATH`, `GITHUB_WEBHOOK_SECRET`; also set `SMEE_URL`.
5. Run `pnpm tunnel` (smee) next to `pnpm dev:server` and `pnpm dev:worker`, then install the App on a sandbox org.

`gh webhook forward` does **not** work for GitHub App webhooks (it only supports repository and organization webhooks). Use smee, or ngrok / cloudflared pointed at `http://localhost:3000/webhooks/github`.

## 5. Architecture

```
GitHub ──POST /webhooks/github──▶ server (Fastify)
                                   │ verify HMAC → INSERT webhook_deliveries ON CONFLICT DO NOTHING
                                   │ + send `github.webhook` job (same transaction)
                                   ▼
                              Postgres (app tables + pgboss schema)
                                   ▲
worker (pg-boss) ── github.webhook job ──▶ handlers registered by modules
```

**How later steps plug in.** Each feature is a folder `src/modules/<name>/` whose `index.ts` exports `webhookHandlers: WebhookHandler[]` and `jobs: JobDefinition[]`. `src/app/registry.ts` is the only file that lists modules. Step 2 added `modules/changes` (the `changes` row and its guarded upsert; store only, no handlers) and `modules/provenance` (trailers, handlers, the `provenance.refresh` job). Step 3 added `modules/intent` (handlers, the `intent.generate` job, card generation, rendering, feedback) and `src/llm/` (the model-client interface, the Anthropic client, the fake). Step 4 added `eval/` with `src/bin/eval.ts`, and step 5 added `modules/policy`, the `src/policy/` library and `src/bin/graft.ts`. Step 6 added `modules/pilot` (reviewer eligibility sync, label-based incident detection, the daily rollup), `src/pilot/` (the CLI-side libraries: baseline, review-time arithmetic, gate, doctor, purge), `src/bin/graft-ops.ts` and `scripts/pilot/`. Expected addition: `src/mcp/` (Phase 1). A module may also export `signalListeners` (see "Policy contract"). Modules import from `config`, `core`, `db`, `github`, `queue` and `webhooks`. They import another module only through its `index.ts`, never its internals.

**Contracts.**

- Webhook handlers must be idempotent, because a failed job retries every handler for that delivery. They must also be fast: DB writes, or enqueueing a follow-up job with `ctx.queue.send(...)`. Slow work such as LLM calls or many GitHub API calls goes into its own `JobDefinition`.
- Deliveries can be processed out of order and concurrently (`WORKER_CONCURRENCY`, retries with backoff, and GitHub itself does not order them), so handlers must tolerate reordering. For order-sensitive state, compare the head SHA or the payload's timestamp and ignore stale events, or use a `key_strict_fifo` queue keyed by installation or PR. Step 1's installation handlers are idempotent but not order-proof (for example a late `added` after `deleted`).
- Code that would persist file contents, diffs or patches does not pass review. Only paths, SHAs, numbers and model prose go in the DB.

**LLM contract (step 3).**

- Modules never build model clients; they use `ctx.llm` (`LlmClient`, `src/llm/types.ts`). `complete()` **returns** a result for every API outcome (timeout, rate limit, refusal, bad JSON, no API key, ...) and throws only on programmer errors, so failure paths are easy to fake and test.
- No prompt, diff, PR title or body, issue text or raw model output is ever logged, put in job data, or stored as such. Logs carry metadata only (model, purpose, token counts, duration, outcome). The DB holds paths, SHAs, numbers and the model's own prose (goal, behavior changes, reasons), nothing else. `test/unit/log-hygiene.test.ts` and I-INT-5 enforce this.
- Token usage is logged per call and stored per card (`intent_cards.input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `llm_calls`, which describe the last run that produced the row); the daily per-repository budget is computed from the append-only `intent_spend` ledger (one row per model run), not from the card rows.
- The system prompt is sent with `cache_control: ephemeral` and is stable per `PROMPT_VERSION`; the volatile diff comes after it.
- All tests use the fake LLM (`src/llm/fake.ts`) or the real client with an injected `fetch`. No test reaches the Anthropic API.
- Model text reaches markdown only through `escapeProse` and `codeSpan` (`src/github/markdown.ts`).

**Feedback (step 3).** Reviewers rate each intent card in two ways. (a) 👍/👎 reactions on the managed comment: GitHub sends no webhook for them, so a scheduled sweep (`intent.feedback.sweep`, cron `GRAFT_FEEDBACK_POLL_CRON`, default every 15 minutes, run by the worker only) enqueues `intent.feedback.poll` for open PRs and recently closed ones, which lists the comment's reactions. A reaction is attributed **by time** to the card that was displayed when it was made (the card with the greatest `published_at` not after the reaction), because one comment shows a series of cards. (b) The buttons "Card is accurate" and "Card is wrong" on the `graft/intent` check run (`requested_action` webhook) belong to exactly the card whose id is in the check run's `external_id`. One vote is stored per `(card, user, source)`; the effective vote per `(card, user)` is the latest across sources; bots are ignored; `is_pr_author` is recorded, and `feedbackSummary` leaves PR authors out by default. **Exception to the payload rule:** the `requested_action` handler only enqueues `intent.feedback.record`, and that job confirms the check run through `checks.get` (our app, name `graft/intent`, an `external_id` that is a card of this repository) but takes the voter and the button from the payload. Residual risk: a replayed captured body can re-assert the same vote, but cannot create a vote for another user.

**Managed PR comment.** Graft keeps exactly one comment per PR, created once and then updated in place (it is not pinned through the API). The contract lives in the doc comment of [`src/github/managed-comment.ts`](src/github/managed-comment.ts), which steps 3 and 5 reuse:

- The body starts with `<!-- graft:managed-comment v1 -->`, then `## Graft`, then one block per section, `<!-- graft:section:<name>:start -->` ... `<!-- graft:section:<name>:end -->`, in the order `intent`, `provenance`, `policy`; unknown sections found in an existing body are kept verbatim after them. A `<sub>` footer closes it.
- Each module writes only its own section through `upsertManagedSection`; every other section is preserved byte for byte. Section markdown may not contain `<!-- graft:` and is capped at 20,000 characters.
- Finding the comment: the stored `changes.graft_comment_id` if it still exists and is ours, else the first of the PR's comments that is ours, else a new comment. **Ours** means the marker is the first line **and** `performed_via_github_app.id` equals `GITHUB_APP_ID`. Because D13 (that field being present on REST comment responses) is unverified against real GitHub, there is a fallback: when `GITHUB_APP_SLUG` is set, a comment authored by the bot login `<slug>[bot]` (type `Bot`) with the marker also counts. A human pasting the marker is never adopted.
- **`withChangeLock(db, changeId, fn)`** (`src/db/locks.ts`): every writer of the managed comment or of per-change GitHub output (check runs) must hold this per-change advisory lock, and must store the comment id in `changes.graft_comment_id` inside the same transaction. The lock is a transaction that holds a pooled connection while requests are in flight, so **do no slow work (LLM calls, diff fetches) inside `withChangeLock`; compute first, then lock, re-check freshness (head SHA and `pr_updated_at`) and publish.**
- **`PermanentJobError(message, reason)`** (`src/queue/errors.ts`): a job throws it when a retry cannot help (deleted PR, lost permission, repo mismatch). The worker logs it and completes the job. `toJobError` in `src/github/errors.ts` maps Octokit errors: 404/410/401/non-rate-limit 403/422 are permanent; 429, rate-limit 403 and 5xx/network errors are retried. It never returns the original error: Octokit errors carry the request body (a rendered card is model output) and pino and pg-boss serialize it, so `sanitizeError` (`src/queue/errors.ts`) rebuilds them as metadata only (name, short message, status, method, route template, request id). The worker sanitizes again before logging and rethrowing, so a job's `pgboss.job.output` and the logs never hold request or response bodies (I-E2E-4).

**Retention of webhook payloads (step 6).** `github.webhook` jobs carry the entire webhook payload, which includes PR titles and bodies, so the `github.webhook` queue alone has `deleteAfterSeconds = 3600` (`WEBHOOK_JOB_RETENTION_SECONDS`, set through `JobDefinition.options.deleteAfterSeconds`): a completed or failed job is deleted one hour after it finished. Every other queue keeps 7 days. **Delivery dedup does not depend on the job**: the `webhook_deliveries` primary key (`INSERT ... ON CONFLICT DO NOTHING`, rows are never pruned) is the dedup, and the deterministic job id is only a second line of defence for the hour in which the job exists, so a redelivery after the job is gone is still `duplicate` and creates no job (I-Q-6). Nothing reads old `github.webhook` jobs: `webhook_deliveries.job_id` is informational, and no code, test or document looks a webhook job up by id after the fact. Two caveats: a job that has not run yet (for example the worker is down) stays queued with its payload until pg-boss deletes it (`retentionSeconds`, 14 days by default), and `intent.feedback.record` jobs (voter login, button) still keep their data for 7 days.

**Webhook replay.** The webhook HMAC covers only the body, so `X-GitHub-Event` and `X-GitHub-Delivery` are unauthenticated: anyone holding one captured signed body can replay it under a new delivery ID (bypassing the `webhook_deliveries` dedup) or under another event name. Mitigations: (1) a payload is only a **trigger**: `pull_request` and `check_run` handlers validate the payload and enqueue a job, nothing else; the job re-fetches the PR from the API and writes only what the API returned (it also checks the PR number and repository id); (2) every handler parses its payload with a zod schema (`parsePayload`, logging issue paths only) and returns on a mismatch, which catches a relabeled event; (3) replays converge: the same body under a fresh delivery ID yields the same dedup key for the downstream jobs (provenance, intent, policy, ...), so none is created within 7 days (their retention), and a later or stale replay only refreshes live state. The `github.webhook` job itself is keyed by the delivery ID and nothing relies on finding it later: its data is the whole payload (PR titles and bodies), so since step 6 pg-boss deletes it **1 hour** after it completes or finally fails (see the retention note below). **The rule for later steps: handlers treat payloads as triggers; jobs write only from API data or from data Graft computed.** Residual risk: an attacker with a captured body can force extra GitHub API calls after the dedup window of the downstream job (7 days), but cannot forge state. A replayed `check_run.rerequested` body is bounded to one re-run per PR per minute: the key is `prov-rerun:{repoId}:{pr}:{floor(now/60000)}` (and `intent-rerun:...` for the intent check), so a flood of fresh delivery IDs enqueues at most one refresh per PR per minute. The work is idempotent and never forges state; only cost is at stake.

Layout: `src/config` (env), `src/core` (clock, logger, context), `src/db` (Kysely, migrations), `src/queue` (pg-boss wrapper, worker), `src/webhooks` (receiver, registry, dispatch job), `src/github` (Octokit factory, the only place an Octokit is built; managed comment; markdown safety), `src/llm` (model clients: the only place an Anthropic client is built), `src/http`, `src/modules`, `src/eval` (the evaluation tool, step 4: a tool, not a module; it imports Graft code only through `modules/intent/index.ts`, `modules/provenance/index.ts`, `modules/changes/index.ts`, `src/llm`, `src/github/client-factory.ts` and `src/github/errors.ts`, never `db`, `queue`, `webhooks`, `http` or `config`), `src/bin` (entry points, including `eval.ts`), and at the repo root `eval/` (JSON Schemas, the synthetic set, the saved baseline and the thresholds). `src/db` imports nothing from `src/modules`. Step 5 adds `src/policy` (the `graft.yaml` library: schema, safe YAML parse, glob checks, the pure evaluator, the GitHub loader and its cache; it imports nothing from `src/modules`), `src/modules/policy` (handlers, jobs, facts, rendering, store), `src/core/glob.ts` (the glob semantics shared by the risk floor, `GRAFT_INTENT_SENSITIVE_PATHS` and `graft.yaml`), `src/core/signals.ts` (cross-module signals) and `src/bin/graft.ts` (the `pnpm graft policy` CLI). Step 6 adds `src/modules/pilot` (handlers, jobs, signal listener, stores), `src/pilot` (CLI-side libraries; it may import `db`, `config`, `github`, `core` and the modules' `index.ts`; `src/pilot` is imported by `src/bin` and, for `normalizeEvent` and `writeFileAtomic`, `src/e2e`) and `src/bin/graft-ops.ts`, which `graft.ts` loads with a dynamic `import()` for `pilot`, `baseline`, `gate`, `incident` and `metrics`, so that `graft policy check` still runs with an empty environment (U-CLI-6). The live e2e runner adds `src/e2e` (a tool like `src/eval`; **import boundary**: it imports only `src/config`, `src/core`, `src/db/client.ts`, `src/db/migrator.ts`, `src/github/{client-factory,errors,rate-limit,managed-comment}.ts`, `src/llm/pricing.ts`, `src/pilot/baseline.ts` (only `normalizeEvent`), `src/pilot/atomic-write.ts`, `src/policy/parse.ts`, `src/eval/terminal.ts` and the modules' `index.ts`, never `src/bin`, `src/queue`, `src/webhooks`, `src/http` or `test/`; only `src/bin/graft.ts` imports it, with a dynamic `import()`; U-LIVE-BOUND-1 enforces both), `e2e/` at the repo root (the sandbox list and the fixtures) and `docs/e2e/`.

**Policy contract (step 5).** The policy is read from the **base branch only**: `heads/<base ref>` is resolved to a commit when the job runs and `graft.yaml` is read at that SHA, never from the PR head or a pull ref (a PR must not loosen the policy that judges it); a PR that edits the policy file is flagged and can never be would-approved. `src/policy` imports no module, so the intent hook, the policy module and the CLI share one parser; the module graph stays one-way through **signals**: the intent job emits `intent_published` and the provenance job emits `provenance_published` after a publish (outside the lock), and since step 6 the intent module emits `feedback_recorded` after it writes votes (the button job after `recorded`, the reaction poll when it wrote at least one row; the pilot module listens and syncs the change's reviewers at most once per hour, the policy listener returns at once), `JobContext.signals` calls the listeners that modules export as `signalListeners`, and the policy module listens and enqueues `policy.evaluate`. Payloads are triggers: handlers validate and enqueue, jobs re-read everything from the API. The `graft/policy` check run **always concludes `neutral`** in Phase 0, so it is not an approval. Nothing from the file is stored but the hash of the parsed policy: rows hold rule indices, reason codes, PR paths, counts, SHAs and logins. Team names are always rendered as code spans, so the comment never notifies a team.

## Provenance trailers for agents

Graft works out who wrote a PR from `Graft-*` git trailers in its commits, with the PR description as a fallback. Agents add them with `git commit --trailer`:

```sh
git commit -m "Fix the retry loop" \
  --trailer "Graft-Agent: claude-code" \
  --trailer "Graft-Model: claude-sonnet-5-5" \
  --trailer "Graft-Task: #42" \
  --trailer "Graft-Session: https://claude.ai/code/session/abc"
```

| Key | Value rule |
| --- | --- |
| `Graft-Agent` | `[A-Za-z0-9][A-Za-z0-9 ._:/@+()-]{0,99}` |
| `Graft-Model` | `[A-Za-z0-9][A-Za-z0-9._:/@+-]{0,99}` |
| `Graft-Task` | `[A-Za-z0-9#][A-Za-z0-9._:/#@+-]{0,127}`; `#42` links issue 42 of the repo |
| `Graft-Session` | an `https` URL, at most 2,048 characters, no credentials, a plain LDH hostname (letters, digits, hyphen, dots; at least two labels; no IP, no `localhost`); `( ) [ ] \| \ `` ` `` `*` are percent-encoded |

Keys are case-insensitive. The trailers must be in the last paragraph of the message (git `interpret-trailers` rules, simplified; the subject alone never counts). A value that fails its rule is ignored and listed as a warning (the warning never repeats the value). **Precedence:** per field, the newest commit with a valid value wins, then older commits, then the PR description (same trailer syntax, last paragraph). If values disagree, the newest wins and all distinct values are shown. **Agent or human:** a PR is agent-authored if any of these holds, in this order: a resolved `Graft-Agent`; the PR author is a GitHub Bot account; the author login is in `GRAFT_AGENT_LOGINS`; a commit has a `Co-authored-by` with an email in `GRAFT_AGENT_COAUTHOR_EMAILS` (default `noreply@anthropic.com`, Claude Code's). Otherwise it is human. Graft stores parsed `Graft-*` values only; commit messages and e-mail addresses are read in memory and never stored.

## Intent cards

For every open PR, Graft writes an **intent card** into the `intent` section of the managed comment and into a `graft/intent` check run (always `neutral` in Phase 0). Reviewers read the card instead of the PR description. It holds:

- **Goal**: one sentence stating what the diff does.
- **Behavior changes**: observable effects, most important first.
- **Out-of-scope edits**: files the goal does not explain (from the writer, plus any the verifier flags).
- **Risk**: `trivial`, `logic` or `sensitive`, shown with where it came from (`rules`, `writer`, `verifier`).

**How it is made.** A writer model reads the PR title and description, the linked issue (`Fixes #N`, the `Graft-Task` issue, or the first `#N`), the file list and the diff. A second call, the verifier, sees the diff, the file list and the card, but **not** the title, description or issue, and checks every claim. The PR description comes from the agent being judged, so it is untrusted input: it is wrapped in nonce-tagged data blocks, the prompts say it is data, and injection markers raise the floor.

**Risk classes and the floor.** The final class is `max(floor, writer, first pass, verifier, logic if the verifier disagrees or fails, logic if injection is suspected)`. **The model can only raise the class, never lower it.** The floor comes from fixed rules over each file's path (and previous path, so renames count both ways), case-insensitively:

| Floor | Rule |
| --- | --- |
| `sensitive` | CI and repository config (`.github/workflows/**`, `CODEOWNERS`, ...); `graft.yaml`; dependency manifests and lockfiles; infrastructure and deployment files; auth, security, crypto and secrets paths; migrations and schema files; paths in `GRAFT_INTENT_SENSITIVE_PATHS`; a deleted test; more than 1,500 changed lines or 50 files; a PR too large to list; an incomplete file list |
| `logic` | a test that lost 10 or more lines; an added binary; more than 300 lines or 15 files; part of the diff not shown to the model (truncated, generated, no patch); text addressed to AI reviewers |
| `trivial` | nothing above matched |

Without a checked card (no API key, model down, budget used up) the risk is at least `logic`, and the card says why.

**"The verifier disagrees"** means that at least one claim on the card was not supported by the diff (unsupported or contradicted), or that the verifier found observable behavior changes the card does not mention. The comment then shows a warning listing them, and the risk is at least `logic`. "Not verified" means the verifier call failed.

**Rating a card.** Click 👍 or 👎 on the Graft comment, or press "Card is accurate" / "Card is wrong" on the `graft/intent` check. Reactions are picked up within 15 minutes. One vote counts per user and card, and the latest wins. The data feeds the 90% accuracy gate.

**Sensitive paths.** Add globs (comma-separated, for example `services/billing/**,**/payments/**`) to `GRAFT_INTENT_SENSITIVE_PATHS`; since step 5 the `sensitive_paths` of the base branch's `graft.yaml` extend the list (the pull request's own copy is ignored; a missing or invalid file leaves the environment value alone). A glob without `/` matches at any depth; a leading `/` anchors it at the repository root. Since step 6 the value is validated at startup with the same checks as `graft.yaml` (a failure names the glob's position and the reason, never the value, and the process exits), including the lookalike check described in [docs/graft-yaml.md](docs/graft-yaml.md); a glob with non-ASCII characters logs one warning.

**Without an API key** (`ANTHROPIC_API_KEY` unset) the service runs and every card shows as unavailable with the rule-based floor.

## Evaluation set

`pnpm eval <command>` measures the quality of the intent cards against hand-labeled pull requests and runs a synthetic set in CI. Nothing here changes the service: the tool lives in `src/eval/` and `src/bin/eval.ts`, never touches Graft's database and never writes into the repo (except the committed synthetic set and its baseline).

```sh
pnpm eval keygen                                   # new GRAFT_EVAL_KEY; keep it in the password manager, never in .env
export GRAFT_EVAL_KEY=...                          # the shell only
pnpm eval init --set ~/.graft-eval/pilot-acme --kind pilot --consent-ref "Acme agreement 2026-11-02" \
     --sensitive-paths 'services/billing/**'
pnpm eval export --set ~/.graft-eval/pilot-acme --repo acme/api --from 2026-06-01 --to 2026-09-30 \
     --auth app --installation-id 123 --sample 50 --dry-run      # drop --dry-run to write the cases
pnpm eval assign-double --set ~/.graft-eval/pilot-acme                # 20% (at least 20) get two labelers
pnpm eval label --set ~/.graft-eval/pilot-acme --as ada               # blind, interactive
pnpm eval agreement --set ~/.graft-eval/pilot-acme                    # Cohen's kappa; target risk >= 0.6
pnpm eval adjudicate --set ~/.graft-eval/pilot-acme --as judge
pnpm eval run --set ~/.graft-eval/pilot-acme                          # fake model: floor + a model that says "trivial"
pnpm eval run --set ~/.graft-eval/pilot-acme --live                   # the only way to reach the Anthropic API
pnpm eval purge --set ~/.graft-eval/pilot-acme --confirm pilot-acme   # when the pilot leaves
pnpm eval:ci                                       # the synthetic set against eval/baselines/synthetic.json
```

Run `pnpm eval` with no command for `run`; `pnpm eval frobnicate` prints the usage. Exit codes: 0 ok, 1 check failed, 2 usage or configuration error, 3 aborted (declined, over budget, rate-limit wait too long).

**Where the data lives.** A case set is a directory (`set.json`, `cases/`, and for pilots `cache/` and `runs/`). The committed synthetic set is `eval/synthetic/` (plaintext, fictional code only). A pilot set is `$GRAFT_EVAL_DIR/<setId>/` (default `~/.graft-eval`) and must be outside every git working tree: the tool walks up from the real path and refuses when it finds a `.git` entry. Files are written with mode 0600 and directories with 0700. Every file in a pilot set except `set.json` and the reports is a sealed AES-256-GCM envelope (`node:crypto`; a fresh random IV per write; the authentication tag is verified before any plaintext is returned; the AAD is `<setId>/<relative path>`, so a file moved to another set or renamed does not open). `GRAFT_EVAL_KEY` is the base64 of 32 random bytes; `set.json` stores only the first 8 hex characters of its SHA-256, to detect a wrong key early. Creating a pilot set needs `--consent-ref`, and `export` refuses a set without one. `purge` deletes the directory and appends `{setId, purgedAt, caseCount, by}` to `purge-log.jsonl`.

**Reports carry no code.** `report.json` and `report.md` (written to `<set>/runs/<runId>/`, or `--out`) hold case ids, classes, rule ids, counts, booleans, tokens and cost, never paths, titles, bodies, diffs or model prose. `pnpm eval show --set <dir> --case <id>` is the local way to read a case; everything it prints goes through `toTerminalSafe` because PR text may hold terminal escape sequences.

**Live runs.** `--live` needs `ANTHROPIC_API_KEY`; without `--live` the key is ignored and the Anthropic client is never built. Before the first call the tool prints an upper-bound estimate and asks `Continue? [y/N]` (`--yes` skips the question; without a terminal and without `--yes` it exits 3). It refuses an estimate above `--max-cost-usd` (default 10), starts a case only if the money and tokens spent so far plus the estimate stay under `--max-cost-usd` and `--max-tokens` (the rest are `skipped_budget` and the report says `complete: false`), and caches results by (inputs, prompt fingerprint) in `<set>/cache/`. Prices are in `src/eval/pricing.ts` (`PRICING_VERIFIED_AT`); check them before a live run.

**Updating the synthetic baseline.** `pnpm eval:ci` compares the whole fake-model report (metrics and per-case rows) with `eval/baselines/synthetic.json` and checks `eval/thresholds.json`. A change to the floor, `combineRisk` or a synthetic case shows up as a diff; when it is intended, run `pnpm eval run --set eval/synthetic --save-baseline eval/baselines/synthetic.json` in the same pull request. The JSON Schemas in `eval/schema/` are generated from the zod schemas (`pnpm eval schema --write`) and a test fails when they drift. The labeling guide is `docs/phase-0/labeling-guide.md`.

## Policy (graft.yaml)

Since step 5 Graft evaluates the repository's `graft.yaml` for every open pull request and **reports** what it would do. Phase 0 enforces nothing: the `graft/policy` check run always concludes `neutral`, a would-approve is not an approval, and team membership is not checked (Phase 1). The reference is [docs/graft-yaml.md](docs/graft-yaml.md); a valid sample is [docs/examples/graft.yaml](docs/examples/graft.yaml) and the editor schema is [schema/graft.v1.schema.json](schema/graft.v1.schema.json).

```sh
pnpm graft policy check graft.yaml          # 0 valid, 1 invalid (one line per error), 2 usage or unreadable file
pnpm graft policy check graft.yaml --json
pnpm graft policy schema [--write | --check]
```

The rules combine like this: every matching rule applies, **block wins**, then any matching `require` wins over `approve`, and `default` applies when nothing matches. An unknown fact (a card that is not ready, provenance not yet computed, an incomplete file list) never loosens a verdict. A missing file, an invalid file or a PR that edits `graft.yaml` is never would-approved. The GitHub Action that lints the file in CI:

```yaml
# .github/workflows/graft-yaml.yml
name: graft.yaml
on:
  pull_request:
    paths: ["graft.yaml"]
permissions:
  contents: read
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4                 # pin to a commit SHA per your org policy
      - uses: actions/checkout@v4
        with:
          repository: <org>/graft                 # HUMAN-TODO: final location
          ref: <pinned commit SHA>
          path: .graft-tool
          token: ${{ secrets.GRAFT_TOOL_TOKEN }}  # only while the Graft repo is private
      - uses: pnpm/action-setup@v4
        with: { package_json_file: .graft-tool/package.json }
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: pnpm, cache-dependency-path: .graft-tool/pnpm-lock.yaml }
      - run: pnpm install --frozen-lockfile --dir .graft-tool
      - run: pnpm --dir .graft-tool graft policy check "$GITHUB_WORKSPACE/graft.yaml"
```

It uses `pull_request`, never `pull_request_target`, and the file is only parsed, never executed.

## Pilots and gate

Step 6 makes onboarding the two pilot teams repeatable and decides the Phase 0 gate from data. **Phase 0 still enforces nothing**: no code path of this step changes a check conclusion, a branch protection or a PR. The runbook is [docs/pilots/onboarding.md](docs/pilots/onboarding.md); the starter policies are `docs/pilots/graft.{service,platform,library}.yaml`; `scripts/pilot/prepare-commit-msg` adds `Graft-*` trailers from `GRAFT_AGENT`, `GRAFT_MODEL`, `GRAFT_TASK` and `GRAFT_SESSION` for any agent harness that can set environment variables.

```sh
pnpm graft pilot doctor --installation 123 [--json]            # 10 DB-only checks, OK/WARN/FAIL, exit 1 on any FAIL
pnpm graft pilot sync-reviewers --installation 123 --since 2026-11-01
pnpm graft pilot sweep-feedback --installation 123             # poll the reactions now (the cron does it every 15 minutes)
pnpm graft pilot allow-list resolve allow.txt --installation 123
pnpm graft pilot purge --installation 123 --confirm acme [--dry-run] [--even-if-active]
pnpm graft baseline --repo acme/api --from 2026-08-01 --to 2026-10-31 [--period baseline|shadow] [--base main]
                    [--max-requests 5000] [--max-wait 15m] [--dry-run] [--auth app|token]   # token: dry run only
pnpm graft gate report --installation 123 --installation 456 --since 2026-11-01 [--until 2026-11-29]
                       [--allow-file allow.txt] [--out dir] [--json] [--check]
pnpm graft metrics rollup --installation 123 --from 2026-11-01 --to 2026-11-29
pnpm graft incident add --repo acme/api --pr 812 [--fix-pr 830] [--occurred-at ISO] [--severity 1-4]
pnpm graft incident list --installation 123 [--json]
pnpm graft incident remove --id <uuid>
```

Every command loads `.env` and the configuration (a bad value exits 2 with the variable's name only), opens the database and stops with `run pnpm db:migrate` when the schema is behind. Exit codes: 0 ok, 1 check failed (doctor FAIL, `gate report --check` FAIL), 2 usage or configuration, 3 aborted (rate-limit wait above `--max-wait`, `--max-requests`, a purge refused: wrong `--confirm`, or an active installation without `--even-if-active`), 4 `gate report --check` with INSUFFICIENT DATA. Output passes through `toTerminalSafe`. Dates are `YYYY-MM-DD` at UTC midnight; `--to` and `--until` are exclusive.

| Command | What it does |
| --- | --- |
| `pilot doctor` | Installation, repositories, deliveries, failed jobs, cards, feedback, policy, budget, rollup and cron checks. Reads the database and pg-boss only (`<schema>.job` with `state = 'failed'` and `data->>'installationId'`, and `<schema>.schedule`). |
| `pilot sync-reviewers` | Backfills `pr_reviewers` (who was requested or reviewed, verified against the repository; see the gate below) for changes opened since a date; run once after deploying step 6 and again after migration 0007, which marks every earlier row unverified. |
| `pilot sweep-feedback` | Polls the reactions on the managed comments of one installation's open and recently closed PRs **inline** (the CLI has no queue; `intent.feedback.sweep` enqueues the same polls every 15 minutes) and prints `polled <n> PRs, <m> votes recorded, <k> skipped`. A permanent error skips the PR; the CLI has no signal listeners, so run `pilot sync-reviewers` afterwards. |
| `pilot allow-list resolve <file>` | Looks up the numeric user ID of every login-only line (`alice` or `@alice`; `@1234` for a numeric login) with `users.getByUsername` (public data, through the installation's token) and rewrites it as `login:id`. The write is atomic: a temp file in the same directory, fsynced, renamed over the original (mode kept). All-or-nothing: an unknown login (exit 3, line numbers only) writes nothing. |
| `pilot purge` | Offboarding: deletes the `installations` row (every app table cascades from it), the installation's `webhook_deliveries` and the pg-boss jobs naming it, then writes one `pilot_purges` row (installation id, counts, time; no login). `OWNED_ROWS` in `src/pilot/purge.ts` lists how each table is counted and I-PURGE-2 fails when a table of `TABLE_NAMES` has no entry. |
| `baseline` | With `--auth token` (a dry run only; reads `GRAFT_BASELINE_GITHUB_TOKEN`, needs no `repositories` row, sends only GET requests) it reads a repository the App is not installed on; the default is `--auth app`. Pulls historical PRs (`pulls.list`, newest first, stopping at the first PR older than `--from`), their timelines and commits, and stores per-PR **numbers** (`review_time_prs`) and aggregates (`review_time_runs.aggregates`) for the baseline period or, with `--period shadow`, the pilot window. Never titles, bodies, paths, logins or SHAs. |
| `gate report` | The Phase 0 gate (below) plus the side metrics, as markdown and JSON (`schemaVersion: 1`). `--out` writes `gate-<until>.md` and `.json` with mode 0600. The allow-list (`--allow-file`; one entry per line, `<id>` or `<login>:<id>`, `#` comments; matched by numeric user ID, the login is a label; a login-only line is an error naming the line number) is recorded only as a count of user IDs and a SHA-256. A line of digits is always an ID; write a numeric login as `@1234` for `resolve` (it becomes `1234:<id>`). |
| `metrics rollup` | Recomputes `metrics_daily` for a range (the worker does the last 7 days every night at `GRAFT_METRICS_ROLLUP_CRON`). |
| `incident add/list/remove` | Records escaped defects per culprit PR number (Phase 1 needs the baseline). |

**The gate.** Card accuracy is computed from **eligible** votes only: the effective vote per (card, user) (the latest across reaction and button), on cards with `status = 'ok'`, by a user who is not the PR author, not a `[bot]` or `GRAFT_AGENT_LOGINS` login, and who is a verified reviewer of that PR or is on the allow-list (user IDs). A verified reviewer (`pr_reviewers.verified`, user ids only, synced from the API; a union over time) is either a **requested reviewer who holds triage or higher permission** on the repository (`repos.getCollaboratorPermissionLevel`, once per user per job; 404 and 403 mean not eligible) or the author of an `APPROVED`, `CHANGES_REQUESTED` or `DISMISSED` review whose `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR` **and** who also holds triage-or-higher permission (a public repository lets anyone review, and any organisation member is a MEMBER). Votes are never matched by login, because a login can be recycled after a rename. The PR author is excluded by user id (`changes.author_id`, from `pulls.get`), so renaming the account does not bring their votes back; bots and `GRAFT_AGENT_LOGINS` are still excluded by login (see §7). Accuracy is `up / (up + down)` with a Wilson 95% interval (`z = 1.959964`). Decision, in order: **FAIL** when `n >= 50`, the upper bound is below 0.90 and the sample is broad enough (at least 6 voters and 2 installations with at least one eligible vote; with fewer the verdict stays INSUFFICIENT DATA); **INSUFFICIENT DATA** when any minimum is missing (150 votes, 50 PRs with a vote, 6 voters, 2 installations with at least 40 votes each, a 14-day window); **FAIL** when card coverage or provenance coverage (PRs opened in the window) is below 98%; a PASS must also hold without the top voter (leave-one-out: the same rule on the votes of everyone else), else INSUFFICIENT DATA with reason `dominant_voter` showing the accuracy and lower bound with and without that voter; at `n >= 400` the point estimate decides (PASS iff at least 0.90); otherwise **PASS** when the point estimate is at least 0.90 and the lower bound at least 0.85, else INSUFFICIENT DATA (`inconclusive`). The report also shows per-installation accuracy, votes by source, dropped votes by cause, card-level accuracy, a `dominant_voter` warning above 40% of the votes, the policy verdict distribution of merged PRs (would-approve share, target 30%), the verifier disagreement and unavailable rates, cost per PR (the new `intent_spend.cost_usd`, computed at spend time from `response.model`; `NULL` means unpriced), the shadow-versus-baseline review time (labelled indicative: shadow mode, Graft blocks nothing; Phase 1 target for agent PRs: at least 50% faster to first approval) and the escaped defects per 100 merged PRs.

**Review time.** A PR's clock starts at the first review request for a team or for a user who is not the author, a Bot or an agent (a request made while the PR is draft or closed takes effect when that pause ends; re-requests never move it), else at `ready_for_review` for a PR opened as draft, else at creation. Draft and closed time is subtracted. Self-approvals and approvals by bots and agent accounts are ignored and counted. Review rounds are the distinct commit ids of qualifying reviews until the first approval. Cells with fewer than 5 observations print as `n<5` (the JSON keeps the numbers).

**Rollup.** `metrics_daily (repository_id, day, rollup_version, counts jsonb)` holds additive counters only (PR counts, cards, verifier statuses, displays, spend, the policy verdict at the merge head, incidents, deliveries; keys in `metricsCountsSchema`). The cron recomputes the last 7 UTC days as an idempotent upsert and deletes rows older than 730 days. Accuracy and percentiles are never rolled up.

**Incidents.** A PR carrying `GRAFT_INCIDENT_LABEL` (default `incident`; `off` disables) that is labeled or merged triggers `pilot.incident.detect`, which reads the **live** PR and accepts only `Reverts <owner>/<repo>#N` (the GitHub revert button) or a line `Graft-Culprit: #N` in the body (at most 5, never the PR itself); with no link it stores one row with no culprit, which `incident add --fix-pr` fills in place.

## Live end-to-end scenarios

`pnpm graft e2e` proves Graft against **real GitHub** (and optionally the real Claude API) in a dedicated, user-owned sandbox repository, `mmornati/graft-sandbox`: a files-only copy of `mmornati/ai-running-coach` plus a `graft-e2e/` fixture directory, a starter `graft.yaml` and a marker file. It runs 10 scenarios (agent and human PRs, CI and policy file changes, an injection attempt, votes and eligibility, a push to `main`, a webhook redelivery) and 2 optional baseline scenarios, checks five system invariants after each (every Graft check `neutral`, one Graft comment per PR, no planted sentinel in Graft's database, `pilot doctor` OK, token spend recorded), verifies 21 assumptions that only fakes had tested so far, and writes a Markdown and JSON report to the gitignored `e2e-runs/`. Each confirmed assumption ticks its HUMAN-TODO item (`report --update-human-todo`). The runbook is [docs/e2e/runbook.md](docs/e2e/runbook.md); the design is [docs/e2e/live-scenarios-spec.md](docs/e2e/live-scenarios-spec.md).

**Two credentials, kept apart.** The *actor* (`GRAFT_E2E_ACTOR_TOKEN`, else `gh auth token`) acts as the repository owner; an optional *outsider* (`GRAFT_E2E_OUTSIDER_TOKEN`, a second account) votes without being the PR author's reviewer. Both live in the shell only: the runner refuses to start if `.env` holds a `GRAFT_E2E_*` key or any actor token value, and no file outside `src/e2e`, `src/bin/graft.ts`, `test/` and `docs/` names those variables. Graft itself still talks to GitHub only as its App.

```sh
pnpm graft e2e setup   [--sandbox o/r] [--create] [--yes] [--invite-outsider] [--dry-run] [--confirm o/r]
pnpm graft e2e run     [--sandbox o/r] [--scenario <id>]... [--run-id <id>] [--dry-run] [--interactive]
                       [--llm auto|live|none] [--max-cost-usd 5] [--lenient-model] [--wait-cron]

                       [--capture] [--timeout-scale 1] [--confirm o/r] [--json]

pnpm graft e2e verify  [--run-id <id>] [--after-retention] [--server-log ...] [--worker-log ...]
pnpm graft e2e report  [--run-id <id>] [--update-human-todo]
pnpm graft e2e cleanup [--run-id <id> | --all] [--yes] [--dry-run]
```

Exit codes: 0 every scenario passed or was skipped, 1 a scenario, invariant or (non-lenient) model assertion failed, 2 usage or configuration, 3 aborted (preflight, guard refusal, budget, declined). `--scenario` takes `s01`..`s10`, `b1`, `b2` and adds the scenario's needs. ## 7. Decisions and library versions

Choices from the step spec: Node 24 ESM, strict TypeScript (NodeNext, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`), `tsx` for dev, Biome for lint and format, Vitest with `unit` and `integration` projects, Fastify, Kysely with `pg` and a static migration provider, `pg-boss` in schema `pgboss`, `pino` with redaction, Postgres 17 on port 55432, GitHub numeric IDs as `bigint` keys (parsed to `number`, throwing above 2^53), `smee-client` for the dev tunnel.

Versions in the lockfile (majors): Fastify 5, Kysely 0.29, pg 8, **pg-boss 12**, pino 10, zod 4, `@octokit/app` 16, `@octokit/rest` 22, `@octokit/webhooks` 14, `@octokit/webhooks-methods` 6, `@octokit/webhooks-examples` and `-schemas` 7, TypeScript 7, Vitest 5, Biome 2, tsx 4, ajv 8, smee-client 5.

### Deviations and additions relative to the step spec

- **pg-boss is v12, not v10.** The assumed API held with these differences: queue and job retry delay is `retryDelay` (seconds), not `retryDelaySeconds` (our `JobDefinition.options.retryDelaySeconds` is mapped to it); retention is `deleteAfterSeconds` (7 days on every queue, except `github.webhook` with 1 hour since step 6; it is a per-job option, `JobDefinition.options.deleteAfterSeconds`); `work()` takes `{ localConcurrency, batchSize }` and a handler over `Job[]`; the transaction option is `db` with an `executeSql(text, values)` adapter (type exported as `Db`), which is what `createPgBossQueue` builds from a Kysely transaction. `start()` installs/migrates its own schema, so the server and worker both call it. Defaults when a job sets no options: `retryLimit 5`, `retryBackoff true`, `retryDelay 10`, `expireInSeconds 300`. They are applied as queue options in `createQueue`. Queue options are re-applied with `updateQueue` on every start, because `createQueue` does nothing for an existing queue (I-Q-3).
- **`singletonKey` does not deduplicate on pg-boss v12 standard queues.** Since v10 the key is only enforced by queue policies `short`, `singleton`, `stately`, `exclusive`, `key_strict_fifo` (or together with `singletonSeconds`); on our `standard` queues it is stored and ignored. `JobQueue.send(..., { singletonKey })` therefore also sets a deterministic job `id` (UUIDv5-style SHA-1 of job name and key; `singletonJobId` in `src/queue/queue.ts`). pg-boss inserts with `ON CONFLICT DO NOTHING`, so a second send with the same name and key inserts nothing and `send` returns `null` (I-Q-2). **The window covers queued, active, completed and failed jobs until they are deleted, 7 days after completion or failure (`deleteAfterSeconds`; 1 hour for `github.webhook`).** A caller that needs a re-run (for example a `check_run.rerequested` for the same SHA) must use a different key, such as one that includes an attempt number or a timestamp. A `null` return means "already enqueued". For webhooks the `webhook_deliveries` primary key is the first line of defence; if the job send returns `null` (job exists, delivery row gone) the existing job id is stored and the outcome is `duplicate`.
- **Empty body returns 400 before signature verification** (spec deviation: the spec has no empty-body rule). It is a cheap check that needs no secret and touches no state; GitHub never sends an empty body (U-WH-8). A delivery id over 100 characters also returns 400 (U-WH-7).
- **Permanent failures are retried** up to `retryLimit`; a non-retryable error type is deferred to a later step. Job data validation runs inside the logged `try`.
- **Kysely 0.29** exports `Migrator` from `kysely/migration`.
- **zod 4**: `z.ZodType<T>` works as in the spec; config defaults are applied before validation (string form).
- **Fastify 5.12**: `disableRequestLogging` is deprecated in favour of `LogController`, which `buildServer` uses (request logging is off; the receiver logs its own outcome line).
- **`githubWebhookJob` is built by a factory.** The job needs the registry's handler lookup and the registry lists the job, so `createRegistry` builds it with `createGithubWebhookJob(registry)` and exposes it as `registry.webhookJob` (also present in `registry.jobs`). The receiver sends `registry.webhookJob`.
- `createPgBossQueue` returns `PgBossJobQueue` (a `JobQueue` plus the `boss` instance the worker needs) and takes a `supervise` flag (false for the server, true for the worker). `buildServer` is `async` and returns the instance without listening.
- Store functions (`getActiveRepository`, `listActiveRepositories`, ...) take a Kysely `Db` or `Transaction` as their first argument.
- Extra files not in the layout: `src/bin/bootstrap.ts` and `src/bin/env.ts` (shared wiring), `scripts/generate-fixtures.ts` (how the fixtures were produced), `pnpm-workspace.yaml` (pnpm 11 build-script allowlist for esbuild), `test/helpers/app.ts`, `test/helpers/stubs.ts`.
- The upstream webhook examples are older than `@octokit/webhooks-schemas` and contain no merged `pull_request.closed`; the generator repairs missing required fields with neutral values and marks the closed PR as merged so all fixtures validate (U-FIX-1).

### Step 2 deviations and additions

- **Library reality.** `@octokit/rest` 22 includes `paginate.iterator` (used for commits and comments; the iterator is stopped early after 3 and 10 pages). `checks.update` takes the check run id and no `head_sha`, so the PATCH body omits it. Nothing else differed from the spec's assumptions. pg-boss 12 only marks a failed job `retry` and bumps `retry_count` when it is next fetched, so I-Q-4 asserts the `retry` state, not the count.
- **D13 fallback (added).** New optional env `GITHUB_APP_SLUG` (`Config.githubAppSlug`). When set, a comment authored by `<slug>[bot]` (type `Bot`) that starts with the marker is accepted as ours when `performed_via_github_app.id` does not match. Without the slug the strict app-id check is the only check. Tested in U-MC-9, U-MC-10 and I-PROV-9. HUMAN-TODO has an item to confirm the field on real GitHub.
- **Dedup key carries `updated_at` and the action.** (Step 3 appended `:{action}`; see T18.) D6 as written would swallow any return to an earlier state within 7 days: `closed`/`reopened` after `opened`, a body edited X to Y to X, or a force-push H1 to H2 to H1 would all hit the key of a completed job, leaving stale provenance. The key is `prov:{repo}:{pr}:{head}:{base}:{bodyHash}:{pull_request.updated_at}` for all five actions, and `pull_request.updated_at` is required in the payload schema (a payload without it enqueues nothing). A replayed body has the same `updated_at`, so replay protection is kept. The cost is one redundant, idempotent job for a title-only edit (the comment comes back `unchanged`, the check run gets one PATCH).
- **In-lock staleness check.** Inside `withChangeLock` the job publishes only if the stored head SHA equals the live head and the stored `pr_updated_at` is not newer than the live `updated_at`. Otherwise two jobs on the same head with different bodies could publish the older body last (I-PROV-10b; the head-moved branch is I-PROV-10c). `updated_at` has one-second resolution, so two edits inside the same second cannot be ordered. The **next** event, or a Re-run of the check, refreshes the output; until then it can be one same-second change behind. The second window (a same-second change with an unchanged head and body, for example `closed` then `reopened`) is now closed by `action` in the dedup key. The title-edit plus close case remains: a title-only edit and a close inside one second share `updated_at`, head and body, and only the action tells them apart.
- **Session host is plain LDH (D14 hardening).** `validateSessionUrl` additionally requires every host label to match `[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?`, at least two labels, at most 253 characters (one trailing dot is tolerated and `localhost.` is rejected), because the hostname is the link text and WHATWG `URL` accepts `` ` * _ ~ ! $ & ' { } = `` in a host. `\`, `` ` `` and `*` are percent-encoded in the href. Trailer whitespace follows git (space and tab only), not JavaScript `\s`.
- **Output-size failures are permanent.** `upsertManagedSection` throws `PermanentJobError` (`invalid_output`) for a marker in the section or an oversize section or comment, instead of retrying a deterministic failure 8 times.

- **Review 3 changes (step 5): the cost model is structural.**
  - **Why.** Review 2's budget charged one unit per step, but a case-insensitive class cost about 60 units of real work (four range scans and two string allocations per character) and the path was case-folded on every call, so a valid 32 KB policy of 200 class-glob rules against 1,000 maximum-length files took about 36 s, and the 3 s wall-clock check ran only inside a single call's own counter.
  - **Cost model (3 lines).** (1) Each path is split and case-folded once per job (cached in the `GlobBudget`, charged one unit per character), and each class is compiled once into a 256-entry table with case folding already applied (code units above 255 are memoised after one charged miss), so a class test costs the same as a literal. (2) Every inner step (one character comparison, class test or DP cell) is exactly 1 unit; per-call setup is charged by size. (3) One `GlobBudget` per job caps total work at **20,000,000 units** and glob x path comparisons at **250,000** (both superseded in review 4: 48,000,000 units, no pair cap), shared by `buildFacts`'s `computeRiskFloor` and `evaluatePolicy` of the same policy job (`evaluatePolicy(policy, facts, { budget })`); when either is spent every later answer is the strict side and `exhausted` is set.
  - **Wall clock.** The deadline is now checked on a counter in the shared budget, every 16,384 units, across the whole job, and is set to **10 s**: it is a bug guard, not part of the model. The budget runs out in about 0.2 to 0.3 s of matching, so on any machine the fuel binds first and results do not depend on load (U-PG-15 gives deep-equal verdicts for 5 s and 600 s limits). If the guard ever fires the worker logs `glob matching hit its wall-clock guard` (hook set in `bootstrap.ts`).
  - **Measured, no network (1,000 files, 1,024-character `path` and `previousPath`, 200 rules plus 20 `sensitive_paths`, 32 KB):** literal shape about 0.19 s for `evaluatePolicy` and 0.42 s for `computeRiskFloor`; class shape (44-entry class) 0.24 s and 0.42 s; mixed (class, two-class two-segment, literal) 0.18 s and 0.44 s.   - **Blocker: the generation clock wrapped (fixed by removing it).** The NFA deduplicated live positions with a module-level `stampClock` stored in `Int32Array`s; past 2^31 ticks (about 2 x 10^9, reached by a long-lived worker, or by a few dozen hostile jobs) every comparison failed and every glob silently stopped matching, process-wide. ### Step 6 deviations and additions

- **Library verification (checked in `node_modules`, pg-boss 12.38.0).**
  - Retention is `deleteAfterSeconds`, a **queue** option (`createQueue` / `updateQueue`) and also a `send` option. A job **copies** the queue's `deletion_seconds` when it is inserted, so `updateQueue` changes only jobs created afterwards. Maintenance deletes a job when `completed_on + deletion_seconds` has passed; failed and cancelled jobs have `completed_on` too, so one rule covers completed and failed jobs. A job that never ran is bounded by `retentionSeconds` (14 days by default), which is left alone.
  - Table and column names used by the doctor and the purge: `<schema>.job` is a partitioned table by queue name (`job_common` is the default partition; deleting from the parent reaches every queue), with `name`, `state` (enum `created`, `retry`, `active`, `completed`, `cancelled`, `failed`), `data` (jsonb), `created_on`, `completed_on`, `deletion_seconds`; `<schema>.schedule` holds `name` and `cron`; `<schema>.queue` holds `name` and `deletion_seconds`. `boss.supervise(name)` runs the maintenance for a queue on demand (used by I-Q-6).
  - Octokit: `pulls.listRequestedReviewers` answers `{ users, teams }`; `issues.listEventsForTimeline` events are normalized by `normalizeEvent` (`reviewed` events carry `submitted_at` and `commit_id`, the others `created_at`; a review request has `requested_reviewer` or `requested_team`); the paginate iterator exposes the response headers, which is how a 10-page timeline cap is detected from `rel="next"`.
- **`github.webhook` retention is 1 hour (the extra task).** `JobDefinition.options` gained `deleteAfterSeconds`; the queue maps it through `resolveJobOptions` (default 7 days) and the webhook job sets 3600 (`WEBHOOK_JOB_RETENTION_SECONDS`). Because a job keeps the value it was inserted with, `queue.start()` also runs `UPDATE <schema>.job SET deletion_seconds = 3600 WHERE name = 'github.webhook' AND deletion_seconds > 3600`, so completed webhook jobs that already exist (7 days) are removed at the next maintenance run instead of lingering for a week (I-Q-6). Dedup does not depend on old webhook jobs (see the retention note in section 5). ### Live e2e runner deviations and additions

Choices made while implementing `docs/e2e/live-scenarios-spec.md`, each where the spec was silent or could not hold:

- **Gate window.** `gate report --since <run day>` needs `--until` after it (the default is the start of today), so s08 passes `--until <run day + 2>`; b1 passes `--to <run day + 1>` as specified.
- **Product fixes found by the first review (both reproduced by the runner).** (1) *The card's task input.* The intent job read `changes.task_id`, which the provenance job writes concurrently; for the same head the card could miss the `Graft-Task` issue (intent won the race) or use the previous head's (after a rewritten history), and the input hash, hence the cache, varied from run to run. Design choice: the intent job now derives the task from **this head's own commits** with the shared provenance parser (`fetchPrCommits` and `computeProvenance`, through `modules/provenance/index.ts`), before any lock, so the card has no dependency on provenance ordering and the input hash is a function of the head. Waiting for or scheduling after provenance would have added a retry path and a latency to every card; reading `change_provenance` only for a matching head would still need a fallback. The extra cost is one `pulls.listCommits` call per card. A 404 on that call leaves the card without a task (the provenance job reports the failure itself). Tests: I-INT-TASK-1 (intent before and after provenance give the same inputs), I-INT-TASK-2 (a trailer-less rewrite does not use the stale task; the original head hits its cache again). s01 asserts `intent_cards.linked_issue_number`, and s07 (d) carries `Graft-Task` again. (2) *Reviewer requests.* `pull_request.review_requested` arrives with `opened`; its sync job could run before the `changes` row existed and returned `skipped`, and once the reviewer reviewed GitHub no longer listed them as requested. Design choice: the job now **creates the change from `pulls.get`** (API data, not the payload) instead of skipping, **reads the request from the API**: the webhook only names a user to look at, and the job records `requested` only if the PR's issue timeline holds a `review_requested` event for that user id (the timeline keeps it after the reviewer has reviewed, the requested list does not) and the permission endpoint gives them triage or higher, so jobs write only API data and a forged or replayed claim records nothing, and it calls `ensureRepository` like provenance and intent (a removed repository is skipped; an unknown one gets its row), and the `provenance_published` signal also enqueues one sync per change (`rev-sync-open:{repo}:{pr}`). No retry loop was added: an upsert has no failure mode that a retry would fix. Tests: I-REV-REQ-1 (a request before the change row exists, then a COMMENTED-only review: the reviewer stays eligible, which is exactly what the gate counts via `pr_reviewers.verified`), I-REV-REQ-2 (no permission, nothing recorded), I-REV-REQ-3 (a claim the timeline does not show records nothing), I-REV-REQ-4 (removed and unknown repositories), I-REV-REQ-5 (`provenance_published` enqueues one sync per change; the listener is now `onChangeSignal`). s08 requests the reviewer at open again, as the spec orders.

## 8. Troubleshooting

- **401 `invalid signature`**: `GITHUB_WEBHOOK_SECRET` differs from the App's webhook secret (or from the one `pnpm webhook:send` reads from `.env`).
- **Duplicate deliveries**: GitHub redelivers on timeouts; the second delivery with the same `X-GitHub-Delivery` returns `200 {"status":"duplicate"}` and enqueues nothing. A delivery that failed with 500 is rolled back, so redelivering it is processed normally.
- **Port 55432 already in use**: another process holds it; stop it or change the host port in `docker-compose.yml` and `DATABASE_URL` / `TEST_DATABASE_URL`.
- **`run pnpm db:migrate`** on startup: the schema is behind; run the migration.
- **`Postgres not reachable ... run pnpm db:up`** from the integration tests: start the container.
