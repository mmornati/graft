## Step 1: base setup

Spec: [step-1-base-setup.md](phase-0/step-1-base-setup.md). Deviations and additions relative to the step spec:

- **pg-boss is v12, not v10.** The assumed API held with these differences: queue and job retry delay is `retryDelay` (seconds), not `retryDelaySeconds` (our `JobDefinition.options.retryDelaySeconds` is mapped to it); retention is `deleteAfterSeconds` (7 days on every queue, except `github.webhook` with 1 hour since step 6; it is a per-job option, `JobDefinition.options.deleteAfterSeconds`); `work()` takes `{ localConcurrency, batchSize }` and a handler over `Job[]`; the transaction option is `db` with an `executeSql(text, values)` adapter (type exported as `Db`), which is what `createPgBossQueue` builds from a Kysely transaction. `start()` installs/migrates its own schema, so the server and worker both call it. Defaults when a job sets no options: `retryLimit 5`, `retryBackoff true`, `retryDelay 10`, `expireInSeconds 300`. They are applied as queue options in `createQueue`. Queue options are re-applied with `updateQueue` on every start, because `createQueue` does nothing for an existing queue (I-Q-3).
- **`singletonKey` does not deduplicate on pg-boss v12 standard queues.** Since v10 the key is only enforced by queue policies `short`, `singleton`, `stately`, `exclusive`, `key_strict_fifo` (or together with `singletonSeconds`); on our `standard` queues it is stored and ignored. `JobQueue.send(..., { singletonKey })` therefore also sets a deterministic job `id` (UUIDv5-style SHA-1 of job name and key; `singletonJobId` in `src/queue/queue.ts`). pg-boss inserts with `ON CONFLICT DO NOTHING`, so a second send with the same name and key inserts nothing and `send` returns `null` (I-Q-2). **The window covers queued, active, completed and failed jobs until they are deleted, 7 days after completion or failure (`deleteAfterSeconds`; 1 hour for `github.webhook`).** A caller that needs a re-run (for example a `check_run.rerequested` for the same SHA) must use a different key, such as one that includes an attempt number or a timestamp. A `null` return means "already enqueued". For webhooks the `webhook_deliveries` primary key is the first line of defence; if the job send returns `null` (job exists, delivery row gone) the existing job id is stored and the outcome is `duplicate`.
- **Empty body returns 400 before signature verification** (spec deviation: the spec has no empty-body rule). It is a cheap check that needs no secret and touches no state; GitHub never sends an empty body (U-WH-8). A delivery id over 100 characters also returns 400 (U-WH-7).
- **Permanent failures are retried** up to `retryLimit`; a non-retryable error type is deferred to a later step. Job data validation runs inside the logged `try`.
- **Kysely 0.29** exports `Migrator` from `kysely/migration`.
- **zod 4**: `z.ZodType<T>` works as in the spec; config defaults are applied before validation (string form).
- **Fastify 5.12**: `disableRequestLogging` is deprecated in favour of `LogController`, which `buildServer` uses (request logging is off; the receiver logs its own outcome line).
- **`githubWebhookJob` is built by a factory.** The job needs the registry's handler lookup and the registry lists the job, so `createRegistry` builds it with `createGithubWebhookJob(registry)` and exposes it as `registry.webhookJob` (also present in `registry.jobs`). The receiver sends `registry.webhookJob`.
- `createPgBossQueue` returns `PgBossJobQueue` (a `JobQueue` plus the `boss` instance the worker needs) and takes a `supervise` flag (false for the server, true for the worker). `buildServer` is `async` and returns the instance without listening.
- Store functions (`getActiveRepository`, `listActiveRepositories`, ...) take a Kysely `Db` or `Transaction` as their first argument.
- Extra files not in the layout: `src/bin/bootstrap.ts` and `src/bin/env.ts` (shared wiring), `scripts/generate-fixtures.ts` (how the fixtures were produced), `pnpm-workspace.yaml` (pnpm 11 build-script allowlist for esbuild), `test/helpers/app.ts`, `test/helpers/stubs.ts`.
- The upstream webhook examples are older than `@octokit/webhooks-schemas` and contain no merged `pull_request.closed`; the generator repairs missing required fields with neutral values and marks the closed PR as merged so all fixtures validate (U-FIX-1).

## Step 2: provenance

Spec: [step-2-provenance.md](phase-0/step-2-provenance.md).

- **Library reality.** `@octokit/rest` 22 includes `paginate.iterator` (used for commits and comments; the iterator is stopped early after 3 and 10 pages). `checks.update` takes the check run id and no `head_sha`, so the PATCH body omits it. Nothing else differed from the spec's assumptions. pg-boss 12 only marks a failed job `retry` and bumps `retry_count` when it is next fetched, so I-Q-4 asserts the `retry` state, not the count.
- **D13 fallback (added).** New optional env `GITHUB_APP_SLUG` (`Config.githubAppSlug`). When set, a comment authored by `<slug>[bot]` (type `Bot`) that starts with the marker is accepted as ours when `performed_via_github_app.id` does not match. Without the slug the strict app-id check is the only check. Tested in U-MC-9, U-MC-10 and I-PROV-9. HUMAN-TODO has an item to confirm the field on real GitHub.
- **Dedup key carries `updated_at` and the action.** (Step 3 appended `:{action}`; see T18.) D6 as written would swallow any return to an earlier state within 7 days: `closed`/`reopened` after `opened`, a body edited X to Y to X, or a force-push H1 to H2 to H1 would all hit the key of a completed job, leaving stale provenance. The key is `prov:{repo}:{pr}:{head}:{base}:{bodyHash}:{pull_request.updated_at}` for all five actions, and `pull_request.updated_at` is required in the payload schema (a payload without it enqueues nothing). A replayed body has the same `updated_at`, so replay protection is kept. The cost is one redundant, idempotent job for a title-only edit (the comment comes back `unchanged`, the check run gets one PATCH).
- **In-lock staleness check.** Inside `withChangeLock` the job publishes only if the stored head SHA equals the live head and the stored `pr_updated_at` is not newer than the live `updated_at`. Otherwise two jobs on the same head with different bodies could publish the older body last (I-PROV-10b; the head-moved branch is I-PROV-10c). `updated_at` has one-second resolution, so two edits inside the same second cannot be ordered. The **next** event, or a Re-run of the check, refreshes the output; until then it can be one same-second change behind. The second window (a same-second change with an unchanged head and body, for example `closed` then `reopened`) is now closed by `action` in the dedup key. The title-edit plus close case remains: a title-only edit and a close inside one second share `updated_at`, head and body, and only the action tells them apart.
- **Session host is plain LDH (D14 hardening).** `validateSessionUrl` additionally requires every host label to match `[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?`, at least two labels, at most 253 characters (one trailing dot is tolerated and `localhost.` is rejected), because the hostname is the link text and WHATWG `URL` accepts `` ` * _ ~ ! $ & ' { } = `` in a host. `\`, `` ` `` and `*` are percent-encoded in the href. Trailer whitespace follows git (space and tab only), not JavaScript `\s`.
- **Output-size failures are permanent.** `upsertManagedSection` throws `PermanentJobError` (`invalid_output`) for a marker in the section or an oversize section or comment, instead of retrying a deterministic failure 8 times.
- **Order inside the lock.** The provenance job upserts the managed comment first and then the check run (T14 lists the check run first); the intent job publishes in the other order since step 4 (see "Step 4 deviations and additions"). This is what I-PROV-8 describes ("comment created, then the check-run POST fails") and it keeps the outcome identical: a failure rolls everything back and the retry adopts the existing comment (T8 3b).
- **Not applied snapshot returns early.** If `upsertChangeFromPull` reports `applied: false` (stored `updated_at` is newer), the job logs `stale` and stops before any commit fetch or publish. That is what I-PROV-3 requires; T14 does not say it.
- **`parseTrailerBlock` also returns `blockTooLong`** (P7 needs a way to reach the `block_too_long` warning); `ProvenanceResult` also carries `truncated` (the renderer needs it and `counts` cannot express it); `persistProvenance` also takes `repositoryFullName` (for the issue URL). When the text was cut from the front (P2) the single remaining paragraph is not treated as a subject.
- **Session URLs must be printable ASCII** (no non-ASCII at all, not even in the path), a stricter reading of "all character sets are ASCII". `|` is percent-encoded as well as `( ) [ ]`, because the URL is rendered inside a table cell (and see the LDH rule above).
- **Rendering of warnings without a field** (`unknown_graft_key`, `block_too_long`): `- <where>: trailer block ignored (<code>)`, or `unknown Graft key ignored (unknown_graft_key)` for an unknown key. When there are no trailers and the PR is truncated, the "no `Graft-*` trailers found" footer still gets the truncation sentence appended.
- **U-REN-7** uses the agent value `octo@bot/@team`: the spec's `@octo/bot` starts with `@`, which the agent character set rejects (a separate assertion checks that it is rejected and never rendered).
- **I-SEC-3** posts the `installation.created` body as `pull_request` twice: unchanged (the receiver ignores it, since the action `created` is not handled) and with `action: "opened"` so the handler really runs and logs `payload_shape_mismatch`.
- **`pnpm db:rollback` reverts one migration** (the latest), as T1 requires; in step 1 it rolled back everything. The test helper `migrateDown` still goes to zero.
- **Extras:** `getActiveInstallation` (installations store, exported) is the "installation exists and is not deleted or suspended" check used by the handlers and the job; `ProvenanceTable.source` gains `pr_body`; `changes.pr_updated_at` and `graft_comment_id` are optional on insert so step 1 tests compile unchanged; a `continue` instead of `return` lets the worker finish a batch after a permanent error (batch size is 1).

## Step 3: intent service

Spec: [step-3-intent-service.md](phase-0/step-3-intent-service.md).

- **Versions.** `@anthropic-ai/sdk` 0.133.0, `picomatch` 4.0.7, `@types/picomatch` 4.0.3 (dev; picomatch ships no types).
- **SDK verified against `node_modules` (T1).** Everything the spec names exists and behaves as assumed: the constructor options `apiKey`, `maxRetries`, `timeout`, `fetch` (and `baseURL`, used by the tests); per-request `{ timeout, maxRetries }`; `output_config: { effort, format: { type: "json_schema", schema } }` on the plain `messages.create` (effort is `low | medium | high | xhigh | max`); system text blocks with `cache_control`; `client.beta.messages.create` with `betas` and `fallbacks: "default"` (`server-side-fallback-2026-07-01` is a listed beta); `usage.{input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens}` (the cache counters can be `null`); `stop_reason` `"refusal"` and `"max_tokens"`; `response.model`; the error classes `APIConnectionTimeoutError`, `APIConnectionError`, `RateLimitError`, `InternalServerError`, `AuthenticationError`, `PermissionDeniedError`, `BadRequestError` and `APIError.status`. Detail the spec did not state: the beta call puts `betas` into the `anthropic-beta` header and adds `?beta=true` to the URL, while `fallbacks` stays in the JSON body (U-LLM-2 asserts exactly that). A 529 arrives as an `InternalServerError`-style `APIError` with status 529 and is retried by the SDK (U-LLM-10). Errors that are not `AnthropicError`s are rethrown as programmer errors.
- **pg-boss 12.38 verified (T1).** `schedule(name, cron, data?, options?)`, `unschedule(name, key?)`, `getSchedules(name?, key?)` and the constructor option `schedule: boolean` exist as named. `schedule` needs the queue to exist (the queue wrapper creates all queues in `start()`), calling it again for the same name replaces the cron (`unschedule` removes it), and the cron expression is only validated by pg-boss at `schedule()` time: `GRAFT_FEEDBACK_POLL_CRON` is checked for shape only (5 fields of digits, `*`, `/`, `,`, `-`), so a cron that passes the shape but is invalid stops the worker at startup. `JobQueue.unschedule` takes the job definition, like `schedule`.
- **The card JSON sent to the verifier escapes `<`** as `\u003c` (still valid JSON). Without it, a writer that echoes the nonce it saw could put a closing data tag into the card and break out of the data block. The spec says "`JSON.stringify` of the validated writer output"; the parsed JSON is identical.
- **Injection rule (R15) ignores format characters.** Before matching, `computeRiskFloor` removes Unicode `Cf` characters and the visible `[U+XXXX]` form that `neutralizeUntrusted` writes for them, so `ig\u200bnore previous instructions` still counts. The spec's patterns are unchanged.
- **Floor reasons.** `FloorReason.paths` holds at most 5 paths as specified, so the check output lists at most 5 per rule (the spec's "up to 50" is an upper bound). The injection reason has no paths and `count` is the number of matching texts; size and listing reasons have none and `count` 0 (the renderer takes line and file counts from `inputs`).
- **Classification order.** Lockfile, then binary, then generated, then "no patch from the API" (T9), implemented once in `classifyFile` (`risk-floor.ts`) and shared by the diff preparation and rule R10. Files beyond the 300th in priority order are summarised per top-level directory; files at the root fall under `"."`.
- **`InputStats.truncated`** is true when the listing is truncated, the PR is too large, or any file is partial (truncated, or omitted for a reason other than lockfile or binary).
- **Nonce seam.** `chooseNonce(canonical, untrustedBlocks, derive?)` in `diff.ts` takes the derivation function as an optional parameter; U-DIFF-10 uses it to force a k=0 collision.
- **A failed escalation keeps what is known.** If the fast writer answered and the strong re-write fails, the unavailable result still carries the first-pass class, its model and the instruction flag, so a first pass of `sensitive` is not lost.
- **Cached cards skip the pending note and the budget.** The cache check (step 5) comes before the outdated-section note (D11) and the budget check, so a cache hit makes no extra GitHub write and counts no tokens.
- **Card rows use the injected clock.** `saveCard` writes `created_at` and `updated_at` from `ctx.clock` (not the database default), so the daily budget and the tests follow the injected time.
- **`intent.feedback.sweep` data** is the empty object, validated strictly. The sweep reads owner and repo from `repositories.full_name`, skips removed repositories, and the poll job re-checks the installation.
- **Feedback summary `since`** applies to the effective vote's `reacted_at` (the vote that wins first, then the time filter).
- **Reactions** with a `null` user are dropped when read; reactions of any user type other than `Bot` count (`Mannequin` and `Organization` included).
- **Models in the card row** are `response.model` as returned by the API (often a dated id), not the requested alias.
- **Pure `generate.ts` exports** also `RETRYABLE` (used by the store to rebuild `retryable` from a stored row) and `EFFORTS`, `MAX_OUTPUT_TOKENS`.
- **Test changes outside the spec's list.** `test/unit/fixtures.test.ts` lists the new `check_run.requested_action` fixture (the generator reuses the upstream example and rewrites it); I-DB-7 now rolls back two migrations (0003 then 0002) because 0003 is the latest; I-CHG-6 uses a replay of `opened` for its first assertion because the action is now part of the key; U-RISK-13's "removed line does not match" half is tested at the card level (U-RISK-13c), because `computeRiskFloor` receives only the added lines; U-INJ-2 includes a file whose name tries to close the section from inside a code span, so that removing the `<!--` rewrite in `codeSpan` fails it. New helper files: `test/helpers/intent-inputs.ts` (pure builders) next to the specified `intent-scenario.ts`. `test/unit/log-hygiene.test.ts` (U-LOG-2) is an extra grep-style test that no logger call in `src/llm` or `src/modules/intent` mentions prompts, diffs, PR text or model output.
- **T18 follow-ups.** Done as specified: provenance re-run key `prov-rerun:{repoId}:{pr}:{minute}` (I-PROV-11), `:{action}` in `refreshKey`, `WarningCode` and `GraftField` moved to `src/db/schema.ts` (`fields.ts` re-exports them; `grep -rn "modules/" src/db/` finds nothing), I-PROV-10c isolated by clearing `changes.pr_updated_at` before the gate is released, and the README wording in the step 2 section. **Mutation check for I-PROV-10c:** with the in-lock head check removed from `provenance/job.ts` the test now fails (the same holds for I-INT-9 and `intent/job.ts`).
- **Mutation checks (DoD)** were run by hand and each made the named tests fail: removing the in-lock head check in `intent/job.ts` fails I-INT-9; dropping the floor term in `combineRisk` fails U-RISK-17, U-RISK-18, U-INJ-1 (and U-GEN-4, U-GEN-13, U-GEN-20); adding the PR text to the verifier message fails U-GEN-15; removing the `<!--` rewrite in `markdown.ts` fails U-MD-4, U-MD-9, U-INJ-2 and U-INJ-4.

## Step 4: evaluation set

Spec: [step-4-evaluation-set.md](phase-0/step-4-evaluation-set.md). (Referred to elsewhere as "Step 4 deviations and additions".)

- **Retry key (T17.1).** `intent-retry:{changeId}:{headSha}:{inputHash16}:{attempt}:{floor(nowMs / 300000)}`, with `nowMs` from `ctx.clock`. A pending-only singleton is not available on our `standard` queues (pg-boss 12), hence the bucket: two triggers for the same inputs within five minutes queue one retry, and a later failure in a new bucket queues its own even when an earlier chain completed. The comment above the send in `job.ts` says so. I-INT-21 now moves the clock by one bucket for its last step (a different delivery in the same bucket is deduplicated); I-INT-22 covers the new rule.
- **The D11 "outdated" note is a display (T17.2).** Migration `0004_intent_display_pending` widens `intent_displays.status` to `ok | unavailable | pending` (down: deletes `pending` rows, restores the old CHECK). After the note's comment write, inside the same lock, the job records a `pending` display of the previous card. `attributeReactions` already treated every non-`ok` display as a dropped one, so a reaction made while the note is shown is not credited to any card. `latestPublishedCard` skips `pending` displays. `markPublished` still compares with the last display of any status, so the next `ok` or `unavailable` publish after a note adds a row. I-FB-10, I-DB-9.
- **Publish order and display time (T17.3).** The intent job now writes the check run first, then the comment, then `markPublished` with a `now` taken right after the comment write. A failed check-run call leaves the old comment and no new display, a failed comment call leaves no new display either, and the pg-boss retry finds the saved card and publishes once. This replaces the "comment first" order for the intent job only (the provenance job keeps its order). I-INT-23.
- **`0003` down (T17.4)** uses `DROP TABLE IF EXISTS` for `intent_displays` and `intent_spend`. **`escapeProse` (T17.5)** keeps the `<!--` rewrite with the "unreachable, defence in depth" comment; no behavior change.
- **New exports.** `modules/intent/index.ts` also exports `fetchIntentInputs`, `promptFingerprint`, `maxRisk`, `RISK_ORDER`, `DOCS_GLOBS`, `TEST_GLOBS`, `globMatcher` and `MAX_OUTPUT_TOKENS`; `modules/provenance/index.ts` exports `computeProvenance` and `fetchPrCommits`. U-PROMPT-1 also asserts `promptFingerprint()` equals the pinned hash.
- **No new dependency.** zod 4's `z.toJSONSchema` (draft 2020-12, verified against `node_modules`) generates the schemas; dates and timestamps are checked with regular expressions instead of `format`, so that a plain JSON Schema validator needs no format plugin. Refinements JSON Schema cannot express are listed in the case schema's top-level `description`.
- **Report details the spec left open.** `status` of a row is `ok | unavailable | skipped` (a case skipped by the budget has status `skipped`). Report thresholds carry a `provisional` boolean; `report.pass` is true only when every result passes (a provisional failure makes it false but exits 1 only with `--strict`). The baseline comparison also ignores the derived fields `thresholds` and `pass` (they depend on the baseline itself) and the per-row `cached` flag; everything else must be equal. Cached rows keep the cost of the result they reuse, `costUsdThisRun` counts only the rows that were not cached. A baseline that does not exist is a usage error with `--check` on the synthetic set, and an explicit `--baseline` that does not exist is always one.
- **Run options added.** `RunOptions.git` is not part of the harness: the CLI fills `report.git` itself. `maxTokens` also gates the pre-run estimate. Budgets and the confirmation apply to `--live` only (fake mode has no real spend); in-flight cases reserve their estimate so that concurrency cannot overshoot `--max-cost-usd`.
- **Export details.** The export counts cases that already exist toward `--sample` (so a re-run of the same export writes nothing, and an aborted one resumes with the rest, re-sampled: see "Resumed export" below), and skips them before stage 1. Exported cases are tagged `size-s|m|l|xl` and `path-sensitive|tests|docs|source` so that the report's per-tag under-classification shows the strata. `--author bot` filters on the list response (`user.type`, `--agent-logins`) and makes no commit request; `--author any` fetches commits only to classify. - **Review 1 changes (step 5).**
  - **Glob matching no longer uses picomatch regexes (blocker).** picomatch compiles `**/*a*a*/**/*a*a*` and similar valid globs to nested overlapping quantifiers; one non-matching path of a few hundred characters took seconds (the §6.2 limits bound each segment, not the interplay across `**`). `src/core/glob.ts` now compiles each glob to segments and matches without backtracking over the input: dynamic programming over (pattern part, path segment), where `**` costs O(parts x segments) in total, and the classic two-pointer wildcard algorithm per segment, which is polynomial. picomatch stays only inside `validateGlob` (compile check) and as the oracle in the tests (U-PG-7, 3,000 generated globs x 30 paths x both case modes, plus the repository's real globs, all equal). Decisions: (1) a path over **1,024 characters or 128 segments** is not matched; the matcher answers its `onLimit` option, which the callers set to the strict side (`true` for `sensitive_paths`, tightening `paths`, the policy-file check and the risk floor's R1 to R7 path rules; `false` for `only_paths` and approve rules, and for test, docs, lockfile and generated classification, where a match would loosen); (2) each call has a budget of 200,000 work units and 20 ms of wall clock and answers `onLimit` when it is spent; (3) `***` (three or more stars in a row) and `]+` are rejected with `glob_invalid` detail 7, because picomatch gives them regex meanings (`[ab]+` repeats, `a/**/***` matches `a`) that the segment matcher does not model; (4) the quirks that are kept on purpose: a trailing `/**` matches the directory itself (`docs/**` matches `docs`) unless the segment before it ends with a star (`*/**` needs a second segment), and `**` inside a longer segment acts as `*`. - **Review 3 changes (step 5): the cost model is structural.**
  - **Why.** Review 2's budget charged one unit per step, but a case-insensitive class cost about 60 units of real work (four range scans and two string allocations per character) and the path was case-folded on every call, so a valid 32 KB policy of 200 class-glob rules against 1,000 maximum-length files took about 36 s, and the 3 s wall-clock check ran only inside a single call's own counter.
  - **Cost model (3 lines).** (1) Each path is split and case-folded once per job (cached in the `GlobBudget`, charged one unit per character), and each class is compiled once into a 256-entry table with case folding already applied (code units above 255 are memoised after one charged miss), so a class test costs the same as a literal. (2) Every inner step (one character comparison, class test or DP cell) is exactly 1 unit; per-call setup is charged by size. (3) One `GlobBudget` per job caps total work at **20,000,000 units** and glob x path comparisons at **250,000** (both superseded in review 4: 48,000,000 units, no pair cap), shared by `buildFacts`'s `computeRiskFloor` and `evaluatePolicy` of the same policy job (`evaluatePolicy(policy, facts, { budget })`); when either is spent every later answer is the strict side and `exhausted` is set.

The budget runs out in about 0.2 to 0.3 s of matching, so on any machine the fuel binds first and results do not depend on load (U-PG-15 gives deep-equal verdicts for 5 s and 600 s limits). If the guard ever fires the worker logs `glob matching hit its wall-clock guard` (hook set in `bootstrap.ts`).

  - **Hostile timings with 60 M (1,000 files with 1,024-character paths, 200 rules + 20 `sensitive_paths`, ms; eval / floor / shared job):** literal that defeats the prefilters 386 / 444 / 483; 44-entry class 439 / 134 / 495; class above code 255 476 / 126 / 522; mixed 406 / 434 / 499; `**` chains on 127-segment paths 429 / 55 / 430. - **Review 6 changes (step 5).**
  - **Blocker: the generation clock wrapped (fixed by removing it).** The NFA deduplicated live positions with a module-level `stampClock` stored in `Int32Array`s; past 2^31 ticks (about 2 x 10^9, reached by a long-lived worker, or by a few dozen hostile jobs) every comparison failed and every glob silently stopped matching, process-wide. There is no counter any more: positions are marked with 0/1 flags, and each flag that was set is cleared again in a `finally` (also when a call stops on a spent budget). Nothing can wrap, go stale or leak between calls. The scratch arrays grow to the largest glob (they were fixed at 128, which a long `GRAFT_INTENT_SENSITIVE_PATHS` glob could exceed). U-PG-19 runs tens of thousands of deep matches, calls that stop half way on budgets of 1 to 300 units, and asserts `matcherScratchClean()`, the matches of `**/secrets/**`, `*.ts`, `infra/**` and `docs/**` before and after, a 100-part glob, and, as a structural guard, that the source has no `stampClock` or stamp array. Because there is no counter to set near 2^31, the test pins the property that made the counter safe instead (no state survives a call). Audit of the other module-level state: the compiled-matcher caches (cleared past 200 keys), the memo for code units above 255 (per class and global caps, cleared together), the per-job `prepared` map (on the budget) and the backstop hook hold no fixed-width counter.
  - **Minor: glued `**` rejected.** `/**.ts`, `a**b`, `x/**y/z` give `glob_invalid` detail 7 ("a `**` glued to other characters is not supported"), because picomatch reads them as "any characters across `/`" and the matcher as `*`; the ambiguous form is rejected so a tightening glob can never match less than its author meant. `**.ts` without a slash is rejected too (it was read as `**/**.ts`).
  - **Minor: a class's own text.** picomatch compiles `[ab]` to `(?:\[ab\]|[ab])`, so `*[ab]` also matches a file named `x[Ab]` (an attacker could otherwise name a file to evade a `secret[ab]` glob). It is modelled, not rejected: a part with a class runs a character-level NFA whose class node is "one character of the set" or "the class's source text". Probed on picomatch: the text alternative exists unless the body holds one of `- * ? + .` (so `[a-c]`, `[a.b]`, `[*]` do not have it); the matcher follows that rule. U-PG-7 now has paths holding class texts and glued stars (deep and flat), U-PG-20 pins both cases.
  - **Nit: units track time.** Every iteration of both NFAs is charged, including when the live set is empty. M23 (removing the empty-set early exit) was a cost-free mutant; now the loop would charge one unit per remaining segment, and U-PG-18 (an anchored glob costs at most 10 units beyond preparation on a 30-segment path) kills it.

## Live e2e runner deviations and additions

Spec: [docs/e2e/live-scenarios-spec.md](e2e/live-scenarios-spec.md).

Choices made while implementing `docs/e2e/live-scenarios-spec.md`, each where the spec was silent or could not hold:

- **Gate window.** `gate report --since <run day>` needs `--until` after it (the default is the start of today), so s08 passes `--until <run day + 2>`; b1 passes `--to <run day + 1>` as specified.
- **Product fixes found by the first review (both reproduced by the runner).** (1) *The card's task input.* The intent job read `changes.task_id`, which the provenance job writes concurrently; for the same head the card could miss the `Graft-Task` issue (intent won the race) or use the previous head's (after a rewritten history), and the input hash, hence the cache, varied from run to run. Design choice: the intent job now derives the task from **this head's own commits** with the shared provenance parser (`fetchPrCommits` and `computeProvenance`, through `modules/provenance/index.ts`), before any lock, so the card has no dependency on provenance ordering and the input hash is a function of the head. Waiting for or scheduling after provenance would have added a retry path and a latency to every card; reading `change_provenance` only for a matching head would still need a fallback. The extra cost is one `pulls.listCommits` call per card. A 404 on that call leaves the card without a task (the provenance job reports the failure itself). Tests: I-INT-TASK-1 (intent before and after provenance give the same inputs), I-INT-TASK-2 (a trailer-less rewrite does not use the stale task; the original head hits its cache again). s01 asserts `intent_cards.linked_issue_number`, and s07 (d) carries `Graft-Task` again. (2) *Reviewer requests.* `pull_request.review_requested` arrives with `opened`; its sync job could run before the `changes` row existed and returned `skipped`, and once the reviewer reviewed GitHub no longer listed them as requested. ## LLM gateways and client-side refusal fallback

Step 1 of [plan/llm-provider-expansion.md](plan/llm-provider-expansion.md).

- **One wire format, any host.** `ANTHROPIC_BASE_URL` points the existing Messages API client at a gateway or cloud that speaks the same API (OpenRouter, Vercel AI Gateway, Requesty, LiteLLM, Bedrock Mantle). `ANTHROPIC_AUTH_TOKEN` sends `Authorization: Bearer` instead of `x-api-key`; at most one of the two may be set. The client passes `null` for every credential and base URL it is not given, so the SDK never falls back to reading `ANTHROPIC_*` from the process environment: the validated config is the only source (U-LLM-13). The log line names the host only, because a URL can carry credentials (U-LLM-15).
- **Model IDs.** Still Claude only, since this is the Anthropic wire format, but a gateway's vendor prefix and a version suffix are accepted (`anthropic/claude-sonnet-5.5`, `us.anthropic.claude-sonnet-5-5-v1:0`). The pattern (`MODEL_ID` in `src/llm/types.ts`) is shared by `src/config` and `src/eval/env.ts`. Such IDs have no entry in `src/llm/pricing.ts`: the service records the run as unpriced (`costUsd` null), and `pnpm eval --live` refuses until a price is added.
- **Server-side refusal fallback on the Claude API only.** The `server-side-fallback-2026-07-01` beta exists on the Claude API alone, so `GRAFT_LLM_REFUSAL_FALLBACK` is ignored when `ANTHROPIC_BASE_URL` is set to any host other than `api.anthropic.com` (`isClaudeApi`, U-LLM-14).
- **Client-side refusal fallback.** `GRAFT_LLM_REFUSAL_FALLBACK_MODEL` (off by default, so nothing changes without it): on `refusal`, `callValidated` repeats the call once on that model, unless the client reports through the new optional `LlmClient.serverRefusalFallback(model)` that it already fell back server-side, or the fallback is the model that refused. The switch is not one of the two D6 attempts, so a call may run three times (refused, fallback, repaired output), still bounded by the deadline. Each call is priced by the model that answered, and the card names that model (U-GEN-32 to U-GEN-35).
- **Diff filtering: no change.** The plan listed "drop lockfiles, generated and vendored files" as new work, but `classifyFile` already leaves lockfiles, binaries and `GENERATED_GLOBS` paths (`dist/`, `vendor/`, minified, snapshots, protobuf output) out of the model input. Filtering more would not save money: every file the model does not see except lockfiles and binaries raises the floor to `logic` (R13 `partial_view`, so that a pull request cannot hide code behind a "generated" path), which moves the PR off the cheap Haiku first pass.

## Workload Identity Federation

Step 1, item 5 of [plan/llm-provider-expansion.md](plan/llm-provider-expansion.md).

- **A third credential, still explicit.** `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID` and `ANTHROPIC_IDENTITY_TOKEN_FILE` (plus the optional `ANTHROPIC_WORKSPACE_ID`) are validated by Graft (`src/llm/federation.ts`, shared by `src/config` and `src/eval/env.ts`) and passed to the SDK as `credentials: oidcFederationProvider({ identityTokenProvider: identityTokenFromFile(path), ... })`. The SDK's own environment resolution (federation variables, `ANTHROPIC_PROFILE`, `~/.config/anthropic`) is never used: `apiKey` and `authToken` stay `null`, and `credentials` is always given when neither is, so the default chain is not consulted (U-LLM-16).
- **Exactly one way to authenticate.** The SDK lets an API key shadow federation. Graft refuses the combination at startup instead, so a leftover `ANTHROPIC_API_KEY` cannot silently win (U-CFG-34). Federation is all-or-nothing; the service account ID is required although the SDK treats it as optional, because the reference lists it as required on the exchange. The identity token path must be absolute. Errors name variables only.
- **Same host for the exchange and the calls.** The token is exchanged at `ANTHROPIC_BASE_URL` (default `https://api.anthropic.com`), which must be https or loopback with federation, since it receives the identity token. The server-side refusal fallback stays on when the host is the Claude API.
- **Token file re-read on every exchange.** Assertions with a `jti` are single use, so the provider never caches the identity token: the SDK's token cache refreshes the minted token in the 2-minute window before expiry and once after a 401, and each refresh reads the file again (U-LLM-17).
- **Exchange failures are API outcomes.** The SDK throws `WorkloadIdentityError` (an `AnthropicError`, not an `APIError`) from inside the request, before any HTTP call, and `AnthropicError` for an unreadable token file; `classify` would have rethrown both as programmer errors. A wrapper maps them to `FederationError` with a failure: 400, 401, 403, a missing `access_token` and an unreadable or empty file are `auth`; 429 is `rate_limited`; 5xx and a network failure (detected in the wrapped `fetch`, not from the message) are `unavailable` (U-LLM-18). The message carries the status only, never the token, path or body. The exchange is outside the request's deadline signal, so it has its own 30 s timeout.
- **Logging and redaction.** The client log line carries `auth: "federation"`, the rule ID and the host (U-LLM-19). The logger redacts `anthropicFederation`, `organizationId`, `serviceAccountId`, `identityTokenFile`, `identityToken`, `assertion` and `access_token`. The e2e runner registers the token file's current contents as a secret; later rotations are caught by the JWT pattern.

## Phase 1 step 1: modes

Spec: [phase-1/step-1-modes.md](phase-1/step-1-modes.md). Decisions D1 to D17 are in the spec; what follows is what the spec left open, what the library check (T1) found, and where the build differs from the spec.

**T1: library verification** (offline, against the fake GitHub API).

- **(a) `octokit.request.endpoint.parse(options)` in `hook.before("request")`** returns the expanded `method` and `url` (full URL, base included) for `octokit.rest.checks.create`, for `octokit.request("PATCH /repos/{owner}/{repo}/check-runs/{check_run_id}", …)` and for `octokit.paginate(octokit.rest.pulls.list, …)`. It does not return a `baseUrl`; the guard reads `options.baseUrl` and strips it (a GitHub Enterprise `…/api/v3` prefix) before matching. `options.url` in the hook is the route *template* for `rest.*` calls, which is what the refusal message uses (after replacing any literal owner/repo and numbers). A `{ref}` parameter is percent-encoded by Octokit (`heads/graft-revert/x` becomes `heads%2Fgraft-revert%2Fx`), and the guard refuses every `%` in a write path (U-MG-2). Step 5 must therefore delete its revert branch with a literal path (`octokit.request("DELETE /repos/{owner}/{repo}/git/refs/heads/graft-revert/" + name, …)` with the owner and repo expanded by the caller), not with `rest.git.deleteRef({ ref })`.
- **(b) The installation-token request does pass through the installation client's `hook.before`**: `POST /app/installations/{id}/access_tokens` is seen by the hook (once per client use, lazily, after the caller's own before-hooks), and `asApp().request("POST /app/installations/…")` passes it too. So the `auth` row is reachable and exercised by every write.
- **(c) A throw in `hook.before` rejects the call without a network request**: the fake's request log stays empty, not even the token call (U-MG-6).

**Choices where the spec is silent**

- **Fan-out inside the claiming transaction.** The pg-boss queue accepts a transaction (`send(..., { tx })`), so `modes.apply` sends its `policy.fanout` jobs in the transaction that claims the `mode_changes` rows and marks them applied. A rollback sends nothing; a repeated run cannot happen for the same rows.
- **`mode set` output.** When nothing changes it prints `no change` and nothing else. After a change it prints the `show` block, then one `note:` line for each key given on the command line whose requested value is not effective (the note names the reason and the missing permission). A shell/worker ceiling warning is printed once, above the first repository. A removed or unknown repository is `unknown or removed repository` on stderr, exit 1, for `show`, `set` and `history`. `--json` prints `permissions: {}` when they were never read (`permissionsReadAt` is then `null`), and the text line says `permissions  not read`.
- **`pilot doctor` is per installation**, so the two new checks (appended after `crons`, always WARN, never FAIL) count for the installation being examined: `permissions` is a WARN when its permissions were not read in the last 48 hours; `modes` is a WARN when a requested mode is not effective (counted by reason). `modes` uses the worker's ceiling from `service_state` when there is one, else the shell's. The Phase 0 doctor tests now expect twelve checks, and their healthy installation has read its permissions.
- **Effective modes in the policy job** are read after `ensureRepository` (a repository created after an `all` install has no row before it), still outside the lock and after the installation check.
- **Mode line when the details are null** (no policy, invalid policy): the text is the mode line alone, so `renderPolicyDetails` returns a string and never `null`. Two Phase 0 render assertions changed accordingly (U-PR-1 gains the line, U-PR-2 expects the line where it expected `null`).
- **`PolicyView.mode`** is required, not optional.

**Deviations from the spec**

- **Ceiling fan-out key.** The spec's singleton key `policy:mode:<repo>:<pr>:ceiling-<ceiling>` would swallow a second change to the same value within the 7-day job retention (report, enforce, report, enforce: the last fan-out would be deduplicated and the check would keep a stale mode line). The repository fan-out therefore carries `ceilingAt` (epoch ms of the change, null for a `mode_change`) and the key is `policy:mode:<repo>:<pr>:ceiling-<ceilingAt>`. `modes.ceiling_fanout` takes `{ at }` for the same reason.
- **The factory's `gate` is optional** and defaults to a gate that allows no Phase 1 write. The spec says the factory "gains `gate`" and callers pass one. `src/e2e` may import only a short list of modules (U-LIVE-BOUND-1) and "no change to the runner" applies, so the runner's own factory cannot be made to pass one. Production wiring (`bootstrap.ts`) passes the real `mutationGate(db, config)` and a logger for refusals; `graft-ops.ts` and `eval/export.ts` pass the refuse-all gate explicitly.
- **One route is added to the table**: `POST /app/hook/deliveries/{n}/attempts`, class `auth`. The live e2e runner's s10 scenario redelivers a webhook with the App-JWT client that it builds from the factory, so a table without it breaks I-LIVE-RUN-1. Graft's own code never calls it, and the class `auth` is not tied to an installation.
- **`installations.refresh_permissions` lives in `src/modules/modes/permissions.ts`**, not `jobs.ts`: the installation handler enqueues it and the modes jobs import the policy job, which imports the installations module, so keeping it in `jobs.ts` would be an import cycle. The daily cron needs a fixed payload, so it runs a second job, `installations.refresh_permissions_all`, that enqueues one refresh per active installation, two seconds apart.
- **N-4 under the default profile.** With a `report` ceiling the effective mode cannot change, so the mode line cannot change either; the suite asserts that the line stays `report` and that the extra `modes.apply` publishes nothing. Under the `max` profile the repository starts at `enforce`, so the sequence is report (a rollback, which is the case that matters) and then enforce again.
- **I-MODE-10 freezes the check details** (a `vi.mock` of `renderPolicyDetails`) because in step 1 the mode line is part of the rendered details, which are already in the facts hash: without the freeze, dropping `policyMode` from the hash would change nothing visible and the mutation check could not catch it. In step 2 the hash term is what keeps the republication correct if the rendered text does not differ.

**Other test changes**: `db.test.ts` and `pilot-ops.test.ts` step down one more migration and count 22 tables (I-DB-1, I-DB-2, I-DB-3 inserts a row into the two new tables); I-PURGE-2 excludes `service_state` next to `pilot_purges` and I-PURGE-1 seeds and counts `mode_changes`; the two tests that call `applyCronSchedules` with a queue that registers two jobs switch the modes crons off; `policy.test.ts` fan-out data gains `scope: "branch"`. The fake GitHub API gains `GET /app/installations/{id}` (`state.installationPermissions`), and `fakeGitHubFactory(api, gate?, onRefused?)`.
